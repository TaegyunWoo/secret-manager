# 구현 진행 기록

계획: [구현 계획](superpowers/plans/2026-10-14-implementation.md).

- 승인된 설계와 사용자 구현 요청을 확인했다. 추가 설계 승인은 필요하지 않다.
- 시작 상태: 설계와 승인 기록만 있으며 Git 저장소와 소스코드, 테스트는 없다.
- 결정: 기존 작업과 충돌할 코드가 없는 새 디렉터리에서 직접 구현한다. Git 초기화 후 구현 브랜치를 사용한다.
- 결정: Node.js 22와 TypeScript, jose, Miniflare로 구현한다. 웹은 프레임워크를 추가하지 않는다.
- 결정: 구현 순서는 보안, 저장소, API, CLI, 웹이다. 실제 배포 및 무료 CPU 측정은 별도 작업으로 남기고 실행 절차를 제공한다.
- 계획 검토: 보안→저장소는 keyring/context 계약, 저장소→API는 Store 계약, API→CLI/웹은 JSON 계약을 공유한다. 파일 소유권은 분리된다. 각 작업의 테스트는 해당 인터페이스의 실패 조건을 확인한다.

## 구현 중 결정

| 결정 | 이유 | 영향 |
|---|---|---|
| 새 디렉터리의 `feat/initial-implementation`에서 작업 | 기존 코드와 Git 저장소가 없어 격리할 변경이 없었다. | 기존 브랜치와의 통합·원격 반영은 하지 않는다. |
| 승인된 설계와 구현 요청을 기준으로 연속 진행 | 사용자가 이미 구현을 요청했다. | 설계의 실제 배포·CPU 측정 단계는 별도로 남는다. |
| 빈 DB 복구 조건에서 감사 기록은 제외 | 인증과 복구 요청 자체가 감사 기록을 만들기 때문이다. | 기존 감사 기록은 유지하고, 같은 ID의 복구 감사 기록은 중복 삽입하지 않는다. 업무 데이터는 덮어쓰지 않는다. |
| OIDC 토큰 발급 주소를 GitHub Actions 호스트와 실제 하위 도메인으로 제한 | runner가 제공하는 발급 경로를 유지하면서 인증 토큰의 다른 호스트 전송을 막는다. | GitHub가 발급 호스트를 바꾸면 CLI도 수정해야 한다. 리디렉션은 따라가지 않는다. |
| CLI 조회 응답 상한을 40 MiB로 설정 | 100개 × 64 KiB 값이 JSON에서 최대 6배로 이스케이프되는 경우를 수용한다. | 최대 응답만큼 메모리를 사용할 수 있다. 값별·키 개수 제한은 그대로 적용한다. |
| 강제 종료로 자식 실행 상태가 불명확한 임시 디렉터리는 보존 | 살아 있는 자식 프로그램이 사용하는 키 파일을 삭제하지 않기 위해서다. | 관련 프로세스가 끝났는지 확인한 뒤 수동 정리가 필요할 수 있다. |

## 검증 범위

자동 테스트는 합성 시크릿, 테스트 서명 키, 실제 로컬 D1과 자식 프로세스를 사용한다. 실제 Chrome에서도 관리 API에 연결해 생성·수정·버전 및 휴지통 복원·가져오기·정책·감사·암호문 백업을 확인했다. PEM 업로드와 다운로드는 BOM과 CRLF를 포함한 바이트를 비교했다.

별도 CLI 통합 확인에서는 빌드된 CLI가 로컬 Worker에서 값을 받아 자식 프로세스에 전달했고, 파일 0600·디렉터리 0700, 자식 종료 코드 7 전달과 종료 후 정리를 확인했다. 이때 cloudflared는 테스트용 실행 파일로 대체했다.

실제 Cloudflare 배포, Google 계정 로그인, cloudflared 인증, GitHub Actions 실행 및 무료 CPU 한도는 아직 검증하지 않았다. [운영 준비](operations.md)의 출시 확인 목록을 따른다.
